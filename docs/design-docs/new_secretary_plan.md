洞察系统终极优化方案：从"提醒机器"到"家庭关系引擎"                                                                                                                                                                                                                                                                                                                         
                                                        
 Context

 当前洞察系统是一个工程精良的"提醒系统"——每天06:00批量采集5类信号(人情/承诺/事件/关系/记忆)，通过Haiku LLM翻译为7种洞察卡片，去重后投递到4个渠道。但它缺乏真正秘书的核心能力：判断力、时机感、深度关怀和持续追踪。

 本方案由四个视角交叉分析得出：AI产品经理(产品价值)、人类社会学家(社会行为本质)、企业秘书(专业实战)、生活秘书/妈妈(真实家庭场景)。不考虑成本和历史债务，以理想架构为目标。

 ---
 一、架构重构：三级生成引擎 + 信息分层

 1.1 三级生成引擎 (替代当前单一LLM管道)

 ┌─────────────┬──────────────┬────────┬──────────────────────────────────────────────┬──────┐
 │    级别     │     引擎     │  延迟  │                   适用场景                   │ 占比 │
 ├─────────────┼──────────────┼────────┼──────────────────────────────────────────────┼──────┤
 │ L1 规则引擎 │ 零LLM        │ <100ms │ deadline提醒、天气联动、周期性账单、固定节令 │ 50%+ │
 ├─────────────┼──────────────┼────────┼──────────────────────────────────────────────┼──────┤
 │ L2 快速生成 │ Haiku        │ ~2s    │ 信号→卡片翻译、简单关联、日常建议            │ 30%  │
 ├─────────────┼──────────────┼────────┼──────────────────────────────────────────────┼──────┤
 │ L3 深度推理 │ Sonnet, 异步 │ ~10s   │ 跨信号综合分析、长期趋势、创意建议、关系诊断 │ 20%  │
 └─────────────┴──────────────┴────────┴──────────────────────────────────────────────┴──────┘

 当前: insight_pipeline.py 所有洞察走单一Haiku管道。
 目标: L1规则引擎处理日常高确定性洞察(天气/账单/药物)，节省LLM预算给L3深度推理(关系趋势/家庭情绪/创意礼物建议)。

 1.2 信息分层 (InformationTriage)

 在信号采集和LLM生成之间插入分层引擎：

 ┌─────────────┬──────────────┬───────────────────────────────────┬────────────────────────────────┐
 │    层级     │     含义     │             处理方式              │              示例              │
 ├─────────────┼──────────────┼───────────────────────────────────┼────────────────────────────────┤
 │ L0 自动处理 │ 秘书自己搞定 │ 直接生成PendingAction，不打扰用户 │ 日程冲突自动协调、已确认的预订 │
 ├─────────────┼──────────────┼───────────────────────────────────┼────────────────────────────────┤
 │ L1 附带知会 │ 不值得单独说 │ 等用户下次交互时"顺便"提及        │ 不紧急的信息更新               │
 ├─────────────┼──────────────┼───────────────────────────────────┼────────────────────────────────┤
 │ L2 正式请示 │ 需要用户决策 │ 主动推送，附带预案选项            │ 人情回礼金额、日程冲突选择     │
 └─────────────┴──────────────┴───────────────────────────────────┴────────────────────────────────┘

 实现: 在 InsightSignalCollector 为每个信号打上建议层级标签。在 InsightPipeline.run_scheduled() 的 enrichment 阶段(第182行后)插入 triage 逻辑。

 1.3 关键文件

 - backend/src/modules/insight/insight_pipeline.py — 核心管道，插入L1规则引擎和triage层
 - backend/src/modules/insight/insight_signal_collector.py — 信号标签
 - 新建 backend/src/modules/insight/rule_engine_insights.py — L1规则引擎
 - 新建 backend/src/modules/insight/information_triage.py — 分层逻辑

 2.1 现有信号增强

 ┌──────────┬─────────────────┬───────────────────────────────────────────────────┐
 │   信号   │      当前       │                       目标                        │
 ├──────────┼─────────────────┼───────────────────────────────────────────────────┤

 │ 关系阈值 │ 固定30天未联系  │ 按关系类型: 至亲7天, 挚友14天, 普通90天, 泛交半年 │

 关系阈值改造: 系统已有 ContactTier(CORE/IMPORTANT/GENERAL 对应 30/90/365天) 和 RelationType(84种)，但 _collect_relationship_signals 完全没使用。应直接用 ContactTier 替代硬编码30天。

 2.2 新增信号源 (按优先级)

 P0 — 节令信号 (SeasonalSignal)
 - 来源: holiday_models.py 已有完整节令基础设施(MAJOR/MINOR/LUNAR_HOLIDAYS, SOLAR_TERMS)
 - 交叉: 节令 × 关系图谱 = 社交义务(春节拜年名单、中秋送礼名单、重阳探望名单)
 - 当前这些完全未接入洞察管道

 P0 — 天气信号 (WeatherSignal)
 - 四位专家一致指出的盲区
 - 触发: 降温>10°→老人孩子加衣; 暴雨→带伞/接孩子; 高温→老人别出门; 花粉季→过敏预防
 - 实现: 外部天气API + 规则引擎(L1, 零LLM成本)

 P1 — 情绪信号 (EmotionSignal)
 - 来源: 对话中的情绪词、行为模式变化(互动质量下降、使用频率变化)
 - 已有: emotional_trend in InsightContextAssembler，但仅影响LLM语气，不触发洞察
 - 目标: 触发正向确认("你和妈妈连续一周都有通话，关系很温暖")和关怀提醒

 P1 — 社交图谱信号 (GraphSignal)
 - 已有: RelationshipEdge 模型(person_a_id/person_b_id/strength)
 - 当前: 信号收集器完全没查询此表
 - 目标: 关键连接人识别、关系降温预警、社交圈重叠发现

 P2 — 家庭经济信号 (FinanceSignal)
 - 周期性开支提醒(房贷/保险/水电/续费)
 - 季节性囤货提醒(双十一、年货)
 - 当前: InsightType.FINANCE 无任何信号收集支撑

 P2 — 健康连续跟踪信号 (HealthTrackingSignal)
 - 当前: health TTL仅3天，一次性提醒
 - 目标: 连续症状跟踪(连续3天说同一个地方不舒服→升级)、季节性预防、疫苗/体检周期

 P3 — 行为模式信号 (BehaviorPatternSignal)
 - 用户每周三都加班晚→周三减少非必要提醒
 - 每天早上7点打开app→最佳briefing投递时间

 P3 — 家庭物资存量 (InventorySignal)
 - "上次买米是两周前"→可能快没了
 - 需要用户输入或智能推断

 2.3 关键文件

 - backend/src/modules/insight/insight_signal_collector.py — 扩展采集器
 - backend/src/modules/relationship/models.py — ContactTier/EventType已定义，需被消费
 - backend/src/modules/member/models/relationship.py — RelationshipEdge需被查询
 - 新建 backend/src/modules/insight/signals/ 目录，每种新信号一个文件

 当前: UserInsightSettings.insights_schedule_hour 只有一个小时值。需要扩展为四波配置。

 3.2 情境感知门控 (DeliveryTimingEngine)

 核心数据结构:
 @dataclass
 class UserMomentState:
     current_activity: Optional[str]   # 从OrchestratedDay推断
     energy_level: str                  # high/medium/low (时段+日程密度)
     receptivity: str                   # open/busy/recovering
     next_transition: Optional[datetime]
     unread_insight_count: int

 投递决策公式: delivery_score = importance × urgency × context_relevance × (1 - interruption_cost)

 ┌────────────────────────────┬──────────┬──────────────────┐
 │          用户状态          │ 允许推送 │       方式       │
 ├────────────────────────────┼──────────┼──────────────────┤
 │ 专注中(连续会议/无交互>2h) │ 仅紧急级 │ Push仅标题       │
 ├────────────────────────────┼──────────┼──────────────────┤
 │ 恢复中(刚结束高强度)       │ 仅L2请示 │ Sidekick轻松语气 │
 ├────────────────────────────┼──────────┼──────────────────┤
 │ 切换中(即将进入下个活动)   │ L1+L2    │ Briefing片段     │
 ├────────────────────────────┼──────────┼──────────────────┤
 │ 空闲/开放                  │ 全部     │ 完整Kanban+Push  │
 └────────────────────────────┴──────────┴──────────────────┘

 5.2 信息追踪线程 (TrackedThread) — 企业秘书的"养信息"能力

 @dataclass
 class TrackedThread:
     id: UUID
     title: str
     thread_type: str  # project/relationship/commitment/preparation
     entity_refs: List[EntitySpec]
     status: str  # monitoring/approaching/active/resolved
     checkpoints: List[Checkpoint]
     created_at: datetime

 工作流:
 1. 新承诺/人情/重要事件 → 自动创建TrackedThread
 2. 每日scheduled run → 检查所有active threads的checkpoints
 3. 到达checkpoint → 生成针对性洞察(基于thread上下文，而非从头分析)
 4. Thread上下文随时间积累(新对话/新事件追加)

 区别于当前: _contextual_reactivation(第801行)只是"回收站恢复"(Jaccard相似度检查dismissed洞察)。TrackedThread是主动的、有计划的持续关注。

 5.3 隐式反馈采集

 当前只有显式反馈(useful/dismiss/defer/never)。新增:
 - 看了但没操作 = 弱负面
 - 点了action但中途放弃 = "方向对方案不够好"
 - 看到洞察后对话中提到相关话题 = 强正面
 - 建议"给妈妈打电话"后用户真的打了 = 洞察成功

 实现: 节令信号与关系图谱在信号采集层交叉，而非依赖LLM发现关联。

 6.3 关系健康度多维模型 (替代单一"天数")

 - 互动质量: 深度对话 > "在吗" (当前 mention_count 只计数不计质量)
 - 单向性检测: 总是你主动→关系可能冷却，继续提醒只会尴尬
 - baseline频率: 区分"两年好友突然三周不联系"(异常) vs "大学同学半年一次"(正常)
 - 趋势而非快照: 从"热→温→冷"的过程比"冷"本身更有价值

 6.5 正向洞察 (20-30%比例)

 - "本月家庭时间增加了30%"
 - "孩子连续练琴10天了！"

 七、家庭生活秘书专项能力

 7.1 "顺路/凑单"优化

 - 看到日程中多个地点 → "接孩子回来路上经过菜场和丰巢，一趟搞定"
 - 利用 OrchestratedDay 的 TimeSlot 和事件地点做路径优化

 7.2 "智能沉默" — AI自主判断"不该说"

 - 某些涉及隐私、面子、家庭敏感地带的洞察自动静默
 - 不同于用户主动suppress，这是AI的主动判断

 7.3 "并行感知面板" — "此刻你盯着的5件事"

 - 不是洞察列表，而是"当前进行时"dashboard
 - 锅里炖着汤(20min后关火) + 洗衣机在转(1h后晾) + 快递在路上 + 4:30接孩子

 7.4 按家人角色差异化

 - 给老人的: 恭敬语气, 字大, 聚焦健康/天气/社交
 - 给孩子的: 鼓励语气, 聚焦学习/成长/习惯
 - 给配偶的: 直接语气, 聚焦日程/人情/家庭决策

 7.5 危机模式 (CrisisMode)

 - 触发: 关键词/模式("孩子发烧""出事了""吵架了")
 - 行为: 暂停所有常规洞察，切换为按步骤处置清单
 - 跟进: 事后追踪恢复状态

 十一、实施优先级 (四位专家共识排序)

 P0 — 立即可做，ROI最高

 1. 洞察内容质量提升: context_hint + 放宽字数 + 动态action_options (改prompt和enrichment)
 2. 信息分层(InformationTriage): L0/L1/L2，减少信息噪音
 3. 关系阈值修复: 用已有的ContactTier替代硬编码30天
 4. 节令×关系交叉: 接入已有的holiday_models到信号采集

 P1 — 核心能力建设

 5. 四波投递节奏: 替代单一06:00批量
 6. 预案链(PrepChain): 从"提醒"到"准备好一切"
 7. 天气信号接入: L1规则引擎，零LLM成本
 8. 趋势检测器: 规则驱动预警
 9. 信息追踪线程(TrackedThread): "养信息"能力
 10. 正向洞察: 20-30%比例的确认型洞察

 P2 — 深度能力

 11. 情绪信号采集: 从对话提取情感信号
 12. 社交图谱信号: 接入RelationshipEdge
 13. 深度推理层(L3 Sonnet): 异步生成跨信号综合洞察
 14. 人生阶段感知: 自动推断，调整策略
 15. 动态优先级: 查询时调分

 P3 — 差异化壁垒

 16. 时光轴: 长期记忆积累
 17. 关系体检报告: 月度综合分析
 18. 秘书自我模型(M4): meta-learning
 19. 危机模式: 紧急切换
 20. 智慧礼物推荐
